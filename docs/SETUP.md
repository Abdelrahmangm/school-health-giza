# إعداد بيئة اختبار فقط

## المتطلبات

Node.js 24، npm، مشروع Supabase فارغ للاختبار. Docker وChromium للاختبارات المحلية. استخدم checkout الموجود؛ كل مهمة سحابية معزولة بالفعل، ولا تنشئ Git worktree إلا بطلب صريح.

```bash
cd /workspace/school-health-giza
export npm_config_cache=/tmp/school-health-npm-cache
npm ci --no-audit --no-fund
npm run typecheck
npm test
npm run build
```

## Supabase

1. أنشئ مشروع TEST بلا بيانات حقيقية. لا تطبّق أي SQL على مشروع إنتاج.
2. طبّق محتوى `supabase/migrations/202610270001_platform.sql` عبر SQL Editor أو migration runner على قاعدة فارغة. **لا تطبق `0001_core.sql` القديم**. جميع الخطوات في transaction. لا يوجد مسار ترقية من المخطط القديم، وإعادة تطبيق migration ليست مدعومة؛ استخدم قاعدة اختبار جديدة.
3. انسخ `.env.example` إلى `.env.local` محليًا، أو عيّن متغيرات بيئة التشغيل في الإعدادات:
   - `NEXT_PUBLIC_SUPABASE_URL`: رابط مشروع الاختبار.
   - `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`: publishable key، أو legacy anon key العام. **لا تستخدم service-role key**. التطبيق لا يحتاجه.
4. عطّل التسجيل العام في Auth. اضبط Site URL وRedirect URLs لتقتصر على عنوان بيئة الاختبار المصرح. اضبط SMTP معتمدًا، وسياسة كلمات المرور وحدود معدل الطلبات. توصيل البريد ومعدلات الإرسال ليست جزءًا من اختبارات Docker.
5. لدعوة/استعادة الحساب، اضبط قالب الرابط على `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=invite` للدعوة، و`type=recovery` للاستعادة. يدعم التطبيق أيضًا `/auth/callback` لتبادل code الخاص بـ PKCE. بعد التحقق ينتقل المستخدم لتعيين كلمة مرور. إرسال الدعوات والاستعادة يتم إداريًا عبر Supabase؛ لا توجد API ذات service-role في الواجهة.
6. أنشئ أول حساب مدير **اختباري** من لوحة Auth، ثم اربطه من SQL Editor بصلاحيات مالك القاعدة:

```sql
-- استبدل UUID فقط بمعرّف حساب الاختبار المنشأ بالفعل؛ لا تضع كلمة مرور هنا.
insert into public.user_profiles(user_id, role, administration_id)
values ('REPLACE_WITH_TEST_AUTH_USER_UUID', 'directorate_admin', null);
```

لا توجد سياسة تسمح للمستخدم بمنح نفسه دورًا. بعد أول مدير استخدم شاشة المستخدمين لربط حسابات Auth التي أنشأها المسؤول بالدعوات، مع إدارة إلزامية لدور مدخل البيانات، وبدون إدارة لأدوار المديرية. تغيير الدور مسجّل في التدقيق؛ لا يمكن للمدير تغيير دوره بنفسه. يدعم النظام أدوارًا مخصصة للتطبيق، ولا يعتمد على `user_metadata` القابل للتحرير.

```bash
npm run dev
# تحقق داخليًا: curl -I http://127.0.0.1:3000/login
```

العمليات الحية لا تستمر بعد استعادة snapshot. أعد تشغيل الخادم عند بداية المهمة. بعد تغيير متغيرات NEXT_PUBLIC في تشغيل إنتاجي اختباري، أعد `npm run build` لأن Next.js يضمّن قيمها وقت البناء. لا تُنشئ رابط معاينة عامًا أو تنشر قبل مراجعة الأمان.

## إعدادات الإصدار ده (الأداء، الدعوات، الاستيراد)

1. **Migration جديدة:** `supabase/migrations/202610270003_performance_users_import.sql` إضافية فقط (مفيش حذف لأي جدول أو عمود أو بيانات). تتطبق بعد 0001 و0002 على مشروع **الاختبار** الأول. على الإنتاج: بعد موافقتك فقط.
2. **متغيرات Vercel (Settings → Environment Variables):**
   - `SUPABASE_SECRET_KEY`: مفتاح Supabase السري (Settings → API Keys → Secret key) أو service_role القديم. **من غير** بادئة `NEXT_PUBLIC_`. بيُستخدم على الخادم بس لإرسال إيميلات الدعوة وتغيير كلمة السر؛ الصلاحيات نفسها بتتكتب بجلسة المشرف العام وRLS. فحص `npm run check:bundle` بيمنع ظهوره في ملفات المتصفح.
   - `SITE_URL`: عنوان الموقع، مثلًا `https://school-health-giza.vercel.app`.
3. **Supabase → Authentication → URL Configuration:** Site URL = نفس `SITE_URL`، وضيف في Redirect URLs: `https://school-health-giza.vercel.app/auth/accept` و`/auth/callback` و`/auth/confirm`.
4. **SMTP:** خدمة البريد المدمجة في Supabase محدودة جدًا (بضع رسائل في الساعة). اضبط SMTP حقيقي (Authentication → Emails → SMTP Settings).
5. **قوالب الإيميل:** القوالب الافتراضية (`{{ .ConfirmationURL }}`) تشتغل كما هي مع صفحة `/auth/accept`. لو حبيت تعرّبها، سيب الرابط زي ما هو وغيّر النص بس.
6. **Disable signups:** لازم يفضل التسجيل العام مقفول؛ الحسابات بالدعوة بس.
7. **مؤشرات الشيتات الأصلية:** الفحص الشامل حاليًا فيه 5 مؤشرات أولية، والشيتات الأصلية فيها حوالي 30. صفحة «البرامج والأعوام» فيها زرار يضيفها كإصدار جديد بعد مراجعتها مع المديرية؛ من غيرها استيراد الشيتات القديمة هيقف برسالة واضحة.

## اختبار تكامل من غير Docker

`scripts/test-integration-local.sh` بيشغّل قاعدة PostgreSQL مؤقتة وملفات Supabase Auth وPostgREST الرسمية وبوابة صغيرة وخادم بريد محلي بيحفظ الرسائل في ملفات بس (مش بيبعت لأي حد). محتاج `PG_BIN` و`GOTRUE_DIR` و`POSTGREST_BIN` (CI بينزّلهم). `SEED_VOLUME=1 PLAYWRIGHT_CONFIG=playwright.perf.config.ts` بيقيس سرعة الصفحات على سنة كاملة من بيانات DEMO.

## اختبارات قاعدة البيانات

`npm run test:db` يستخدم PostgreSQL 17 في حاوية مؤقتة بلا منفذ منشور. توجد fixture مبسطة لـ `auth.uid()` و`auth.users` لاختبار RLS والدوال بصفة authenticated/anon. بيانات DEMO تُلغى بـ rollback، والحاوية تُحذف حتى عند الفشل. هذا لا يثبت إعداد خدمة Auth المستضافة.

## اختبار التكامل المحلي

`bash scripts/test-integration.sh` ينشئ شبكة وحاويات مؤقتة: PostgreSQL 17، Supabase GoTrue v2.177.0، PostgREST v12.2.3 وNginx 1.28. ينشئ مفتاح JWT عشوائيًا لبيئة DEMO فقط، وأربعة حسابات `demo-*@example.test` دون بريد فعلي، ويشغّل Next.js على 3001 وواجهة API على 127.0.0.1:55433. يعتمد على signup/autoconfirm **فقط داخل الحاويات القابلة للحذف**، وليس إعدادًا مقترحًا لمشروع Supabase.

تتحقق الاختبارات من الدخول الفعلي بكلمة مرور، وحفظ بلاغ وإرساله واعتماده ثم تعديله، وعزل إدارة أخرى، وصلاحية المشاهد، واعتماد المستهدفات، ورفض كتابة عبر REST مباشرة. تُحذف الحاويات والشبكة وملفات المفاتيح المؤقتة عند الانتهاء. لم تُختبر رسائل الدعوة أو SMTP أو مشروع Supabase مستضاف. CI يشغّل الاختبارات نفسها دون أسرار خارجية.

## مشاكل شائعة

- `/setup`: متغيرات Supabase غير مضبوطة؛ لا يعني أن قاعدة البيانات متصلة.
- حساب بلا profile: يعاد للدخول برسالة صلاحية؛ اربطه من المسؤول.
- فشل حفظ بعد الإغلاق: استخدم إعادة فتح مبررة بواسطة مدير المديرية، بحد أقصى سبعة أيام.
- نسخة نشطة موجودة: عدّل المسودة الحالية بدل إنشاء نسخة مكررة.
- برنامج تغير بعد إنشاء مسودة: افتح المسودة وأعد حفظ الصفوف على آخر إصدار قبل الإرسال.
- تحديد حدود الفترة: كل تاريخ يمثل بداية أسبوع الأحد؛ YTD هو الفترة من أول أسبوع بالعام حتى أسبوع النهاية.
- API GitHub ممنوع: Git read/push منفصلان عن صلاحية إنشاء PR. لا تضع tokens في ملفات المشروع.

لا توجد seed تشغيلية. migration ينشئ الإدارات والبرامج والعام فقط، دون حسابات أو بلاغات أو أرقام DEMO. بيانات DEMO محصورة في الاختبارات المؤقتة.
