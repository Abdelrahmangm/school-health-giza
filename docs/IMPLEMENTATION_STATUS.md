# حالة التنفيذ — فرع المراجعة

التاريخ: 2026-10-27 بتوقيت القاهرة. لم يُنشر التطبيق، ولم تُستخدم بيانات حقيقية. المستودع الأصلي كان حزمة متطلبات وخط أساس SQL فقط؛ بُني التطبيق من الصفر دون مصدر Lovable.

## الملفات المنجزة

| المسار | ما يعمل |
|---|---|
| `app/(portal)/page.tsx` و`components/filters.tsx` | لوحة مؤشرات وفصل الرسمي/الأولي والعام/الأزهري والبرنامج والصف والفترة والإدارة |
| `app/login`, `app/auth`, `proxy.ts`, `lib/supabase.ts` | تسجيل دخول بكلمة مرور، تجديد cookie، استقبال الدعوة/الاستعادة وتعيين كلمة المرور |
| `app/(portal)/reports`, `components/report-form.tsx` | بلاغ موحد، مسودة وصفوف تفصيلية، إرسال، إعادة للتصحيح، اعتماد، اقتراح تعديل، سجل النسخ وإعادة فتح مبررة |
| `app/(portal)/targets` | اقتراح المستهدفات ومراجعتها وحفظ إصداراتها وتاريخ نفاذها |
| `app/(portal)/programs` | أعوام دراسية، برامج وصفوف ومؤشرات بإصدارات مرتبطة بالعام، والتفعيل/التعطيل دون حذف التاريخ |
| `app/(portal)/analytics`, `app/export` | مقارنة الإدارات والاتجاه واكتمال الأسابيع بما فيها الأسابيع دون بلاغات، CSV تحليلي، لقطات بيانات محفوظة لا تتغير باعتمادات لاحقة |
| `app/(portal)/users`, `app/(portal)/audit` | ربط مستخدمي Auth بأدوار وإدارات، حماية الدور الذاتي، قراءة سجل التدقيق للمدير |
| `app/(portal)/imports`, `components/import-form.tsx` | معاينة CSV مجمّع، كشف تكرار/أرقام/صفوف غير صالحة، وحفظ staging فقط |
| `supabase/migrations/202610270001_platform.sql` | مخطط كامل، reference data، RLS، منع الكتابة المباشرة، RPCs ذرية وصلاحيات على مستوى الخادم وقاعدة البيانات |
| `lib/domain.ts`, `tests`, `supabase/tests`, `scripts` | حساب القاهرة والإغلاق والتجميع/المستهدفات، واختبارات الوحدة والقاعدة والمتصفح والتكامل المحلي |
| `.github/workflows/ci.yml`, `.env.example`, `docs/SETUP.md`, `docs/ARCHITECTURE.md` | CI ودليل تشغيل وتهيئة ومراجعة؛ بدون أسرار حقيقية |

أضاف `next dev` قسم قواعد Next.js المُدار إلى نهاية `AGENTS.md`، مع الحفاظ على تعليمات المشروع الأصلية.

## التحقق

- TypeScript والبناء الإنتاجي: ناجحان.
- Vitest: **22 اختبارًا ناجحًا**، تشمل حدود الوقت والتوقيت الصيفي، العزل المنطقي، فصل القطاعات وKG2، النسخ والمستهدفات التاريخية، CSV injection والاستيراد.
- PostgreSQL 17: **44 تحققًا ناجحًا** بـ RLS وRPCs فعلية على قاعدة مؤقتة، مع fixture لـ Auth. لا يعني ذلك اختبار إعداد مشروع Supabase المستضاف.
- متصفح الإنتاج بدون إعداد Supabase: **4 اختبارات ناجحة** بعد البناء النهائي.
- تكامل محلي GoTrue + PostgREST + PostgreSQL + Next.js: نجحت دورة الدخول والإرسال والاعتماد والتعديل واعتماد المستهدف واللقطة/التصدير وعزل الإدارة وصلاحية المشاهد عبر REST. نجح التشغيل الموسع أيضًا لشاشات الإدارة وتجهيز الاستيراد.
- `npm audit --omit=dev`: **لا توجد ثغرات معروفة في حزم التشغيل** وقت التحقق؛ ليس هذا تدقيقًا أمنيًا مستقلًا.
- CI مضاف؛ تُراجع نتيجة التشغيل البعيد في Pull Request، ولا تُستنتج من نجاح التحقق المحلي.

## غير المكتمل / ما يحتاج مراجعة خارجية

1. **مطابقة وتصدير ملف الوزارة الرسمي:** الملف الأصلي غير متاح. المسار يعيد 409 ولا يخمن أسماء الأعمدة أو ترتيبها. جدول mappings مجرد أساس؛ يلزم بناء المطابقة واختبارات workbook فعلية قبل فتح التصدير.
2. **مشروع Supabase المستضاف:** لم تُطبق migration على مشروع خارجي ولم تُضبط متغيراته. قاعدة الاختبار المحلية تثبت المسارات الرئيسية فقط. يلزم مشروع TEST فارغ ثم مراجعة إعدادات Auth/RLS وTLS والدومينات.
3. **البريد والدعوات:** مسارات استقبال الدعوة/الاستعادة موجودة، وإرسال الدعوات إداري عبر Supabase. لم يُختبر SMTP أو تسليم الرسائل أو MFA أو دورة الدعوة عبر بريد فعلي.
4. **البيانات السابقة:** staging يعمل للصيغة الموثقة فقط؛ لم يُنفذ تحويل تلقائي إلى البلاغات أو استيراد XLSX أو مطابقة المصادر التاريخية الثلاثة. لا يوجد ربط قراءة أو كتابة بـ Google Sheets. توسيع الاستيراد إلى catalog مخصص يحتاج تعديل المعاينة ومراجعتها.
5. **المراجعة الأمنية والتشغيل:** لم تُعتمد قائمة مؤشرات الفحص الشامل من المديرية. يلزم اختبار الأدوار على منصة الاستضافة، تدقيق مستقل، سياسة الاحتفاظ والنسخ الاحتياطي، وموافقات الجهة. `DEPLOYMENT_CHECKLIST.md` يفصل الشروط.
6. **التزامن والحجم:** انتقالات الاعتماد ذرية، لكن حفظ مسودتين متزامنتين يتبع آخر كتابة؛ لا توجد آلية optimistic concurrency للمسودة. القراءة مجزأة بحد 100 ألف صف، والتجميع الحالي في خادم Next.js؛ يلزم تجميع SQL/ترشيح وفهارس واختبار حمل قبل التوسع.

هذه ليست موافقة أمان أو إعلانًا بأن جميع معايير `CODEX_TASK.md` مكتملة. جميع الأرقام والحسابات التجريبية داخل حاويات الاختبار القابلة للحذف فقط، ولا توجد seed تشغيلية أو بيانات شخصية للطلاب.

المستودع الحالي **عام** حسب GitHub. لم أغيّر خصوصيته؛ يلزم تقييد الوصول قبل أي تشغيل أو مشاركة إعدادات حساسة. لا يحتوي هذا الفرع على بيانات حقيقية أو مفاتيح خاصة.

## تحديث: الأداء وإدارة المستخدمين والاستيراد (فرع `feature/performance-users-import`)

- **الأداء (مقاس على سنة DEMO كاملة: 13 إدارة × 50 أسبوع، ~15600 صف):** صفحة إدخال/فتح البلاغ من 6.3MB و~1 ثانية إلى 43KB و~0.13 ثانية؛ لوحة التحكم 687→236ms؛ البلاغات 899→147ms؛ السجل 1.1MB→117KB. السبب: كل صفحة كانت بتنزّل كل الجداول وتبعتها للمتصفح. دلوقتي: تجميع في PostgreSQL (`report_facts`)، استعلامات مخصصة لكل صفحة، ترقيم صفحات، جلسة واحدة لكل طلب، سياسات RLS بـ InitPlan وفهارس.
- **المستخدمين:** دعوة بالاسم والإيميل والدور والإدارة، المستخدم يختار كلمة سره، نسيت كلمة السر، تغيير كلمة السر، إعادة إرسال الدعوة، إيقاف حساب مع حفظ تاريخه. الصلاحيات في RPCs للمشرف العام فقط وRLS.
- **الاستيراد:** Excel/CSV بنفس شكل شيتات البلاغ الأصلية، مطابقة أعمدة، تطبيع أسماء الإدارات، فصل العام/الأزهري، كشف التكرار، تحويل التراكمي لأسبوعي، مقارنة بالأرقام الرسمية، ثم تحويل لمسودات فقط (مش اعتماد)، والمستهدفات اقتراحات فقط، وكل خطوة في سجل المراجعة.
- **التحقق:** 58 اختبار وحدة، 91 تحقق قاعدة بيانات، 4 متصفح بدون إعداد، 2 تكامل كامل (منها دعوة بإيميل حقيقي على خادم بريد محلي)، فحص عدم تسرب الأسرار للمتصفح، `npm audit` بدون ثغرات.
- **ما زال معلقًا:** تصدير نموذج الوزارة (الملف المرجعي غير متاح)، اعتماد قائمة مؤشرات الفحص الشامل من المديرية، تطبيق الـ migration على مشروع الإنتاج بعد موافقتك.
